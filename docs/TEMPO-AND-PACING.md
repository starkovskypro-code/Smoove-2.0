# Версия 0.4: ускорение темпа, сглаживание и частота

## Настройки

| Настройка | Значение / эффект |
|---|---|
| Ускорение от темпа, % | 0–100%, по умолчанию 35%. Дополнительный множитель расстояния для быстрого вращения, вплоть до +35% при исходном значении. Медленные одиночные шаги сохраняют точность; 0 отключает функцию |
| Сглаживание серии, % | 50–200%, по умолчанию 100%. Масштабирует время разгона и торможения вместе. Больше — мягче и дольше реакция/хвост. Расстояние завершённого жеста не меняет |
| События, Гц | 60/120/240/500, по умолчанию 240. Управляет периодом отправки небольших событий, а не FPS чужого приложения |

Рекомендуемая начальная настройка: ускорение 35%, сглаживание 120–140%, частота 240 Гц. Если ощущается задержка реакции — уменьшить сглаживание. 500 Гц можно сравнить на дисплее с высокой частотой; большее число событий увеличивает нагрузку и не гарантирует визуального улучшения.

Сглаживание связано с существующими разгон/торможение: эффективные постоянные времени равны значениям этих полей, умноженным на процент. Поле не маскирует отдельную анимацию в receiver; он по-прежнему отображает события общего движка напрямую.

## Реализация

Темп вычисляется из суммы абсолютных единиц колеса за время с экспоненциальным затуханием 200 мс. Это не число пакетов: высокоточное колесо не получает ложное ускорение только за счёт дробления событий. Плавная кривая gain начинает расти после порога темпа, ограничивая только дополнительный бонус, а не скорость свободного вращения. Смена направления сбрасывает оценку темпа, не сбрасывая модель положения/скорости. Множитель обычного расстояния применяется отдельно.

Планировщик использует `CreateWaitableTimerExW` с `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` и однократный `SetWaitableTimerEx`. Таймер активен во время движения; в простое worker ждёт входной сигнал. Нет spin-loop и глобального изменения разрешения таймеров. Ввод и отмена прерывают ожидание; выдача ограничена выбранным периодом, пропущенные тики не воспроизводятся бурстом. Задержка ОС/системная нагрузка остаются возможными.

Документация Microsoft сверена: high-resolution flag доступен с Windows 10 1803; отрицательное due time означает относительное ожидание в единицах 100 нс; точность зависит от аппаратной платформы. Это не гарантия 240/500 кадров/сек в Telegram/браузере или на экране.

## Проверки

- Release-сборка без ошибок/предупреждений; пройдены существующие проверки источника, сумм, free-spin, разворотов, паузы и отмены.
- Ускорение 35% в модели: медленный темп — gain 1,000; быстрый — 1,337; free-spin — 1,342. Бонус не ограничивает рост основной скорости.
- Отдельно проверены отключение ускорения, сброс после паузы/разворота и сохранение расстояния при увеличении сглаживания.
- Self-contained native check: raw control 20 paint-изменений против 577 при преобразовании; на установившемся участке 309 изменений, max gap 9,77 мс. В версии 0.3 тот же участок давал около 100 изменений с max gap 21 мс.
- Настройка частоты проверена на одинаковом участке 0,6 сек: 35 paint-изменений при 60 Гц, 243 при 500 Гц. Расстояние обеих серий сохранено.
- UI-настройка ускорения проверена через реальную ветку: 16 импульсов −120 с интервалом около 50 мс дали 2388 вместо 1920 единиц, примерно +24,4%; бонус растёт постепенно с началом серии.
- High-throughput: 80 входов −1200, все −96000 доставлены без отмен. Смена частоты не восстановила ограничитель версии 0.2.

Это измерения paint callback диагностического окна, не числа предъявленных дисплеем кадров. Итоговое ощущение на Logitech и целевом дисплее требует пользовательской проверки. Ускорение намеренно меняет общую сумму выходных дельт; проверки точного равенства входа/выхода выполняются с ускорением 0, а проверка gain — с 35%.

После исправления DPI повторная проверка финальной публикации прошла: 36 paint-изменений при 60 Гц против 246 при 500 Гц за 0,6 сек; ускоренная серия 2389/1920; 96000 единиц fast-spin доставлены без отмен. В установившемся участке 294 paint-изменения, max gap 15,81 мс. Разница с предыдущими замерами показывает влияние планировщика и нагрузки; фиксированный FPS не обещается.

Один ранний native-прогон не прошёл проверку хвоста после дрожания курсора; добавлена подробная диагностика. Следующие два прогона, включая опубликованный exe, прошли. Этот единичный сбой не считается доказанно устранённым только из-за повторного PASS; диагностика сохранена для воспроизводимого повтора.

Повторные Telegram-проверки версии 0.4 не подтвердили визуальный результат: сначала выявлено несовпадение DPI-контекста thread-pool и физических координат UIA/hook, затем текущая область была на краю списка, а последняя попытка не нашла открытый HistoryWidget. Координатные вызовы приведены к per-monitor physical context; чат-тест теперь прокручивает вверх. Ни доставка событий без перемещения сообщения, ни отсутствие текущей переписки не засчитываются как PASS. Сравнение в тестовом receiver прошло; текущая переписка Telegram на версии 0.4 остаётся непроверенной, несмотря на успешную проверку предыдущей версии.
